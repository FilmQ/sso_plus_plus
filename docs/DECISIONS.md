# Decisions and deviations

Each entry tells what we decided, why, and which part of the SA report it affects, so that the team can write it
back into the report. `docs/spec/` does not change.

| ID | Date | Decision | Why | Report section |
|---|---|---|---|---|
| D-001 | 2026-10-14 | **Stack.** PostgreSQL 16 in Docker Compose; a Dart server (`shelf`, `postgres` package) for Controller, Model, Repository and `DBConnector`; Flutter (Material 3) for the user app and the console, on web and mobile. Tests: `dart test` and `flutter test`. This replaces the Node.js, Express and React default of the brief. | The team chose Flutter. A Flutter web app cannot open a PostgreSQL connection, so a server is necessary. A Dart server keeps one language. | 2.20 (Software platform) |
| D-002 | 2026-10-14 | **Client and server.** The Page classes are Flutter widgets. They call the server over HTTP (JSON). The Controller, Model, Repository and `DBConnector` classes are in the server, with the report's class and method names. | The report's MVC layers stay the same. Only the line between Page and Controller is a network call. | 2.13, 2.18 |
| D-003 | 2026-10-14 | **Login.** New infrastructure table `UserAccount` (role `USER`, `OFFICER` or `CONSULTANT`, login name, bcrypt password hash from `pgcrypto`, link to `insured_id`, `officer_id` or `consultant_id`), in `server/db/migrations/002_user_account.sql`. Login is infrastructure, not a use case. A user signs in with the national ID, staff with the e-mail address. The server gives a signed token (HMAC-SHA256, 12 hours); it keeps no session table. The user app accepts only `USER`; the console accepts `OFFICER` and `CONSULTANT`. Seed accounts (password `Password123`): the five sample users, officer 1 and consultant 1 (`server/db/seeds/001_user_accounts.sql`). Officers and consultants come only from seed data. Confirmed by the spec owner: `UserAccount` stays infrastructure and does not go into the report tables. | The report has no login use case and no place for passwords (07-open-questions.md, item 1). The team agreed on 2026-10-14. | 2.11, 2.17, 2.22 (site map) |
| D-004 | 2026-10-14 | **Migrations.** Migration 001 is `docs/spec/database/schema.sql` without changes. Infrastructure migrations are in `server/db/migrations/`, infrastructure seeds in `server/db/seeds/`. `dart run bin/migrate.dart` deletes the `public` schema and loads all files again. | One copy of the report's schema. The tool works the same for the dev and the test database. | 2.17 |
| D-005 | 2026-10-14 | **Test database.** The tests use a second database, `sst_test`. Each test file loads it again; each test runs in a transaction that rolls back. | The tests always start from the seed rows. Work in the dev database does not change the results. | 2.25 |
| D-006 | 2026-10-14 | **SQL text.** `server/tool/gen_sql.py` copies the 56 statements from `queries.sql` into `server/lib/repository/sql/`. The test `queries_match_report_test.dart` makes sure that they stay the same. A Query ID with more than one statement is a list; the Repository runs the list in one transaction. | Rule 2 of the brief: the SQL is the report's SQL. | 2.16 |
| D-007 | 2026-10-14 | **Parameters.** `DBConnector` changes `:name` to `$n` and sends the values without a type, so PostgreSQL finds the type from the SQL. String literals, comments and `::type` casts do not change. | The SQL text stays as in the report. | 2.16 |
| D-008 | 2026-10-14 | **Guarded Query IDs.** In Q3.3, Q3.5, Q3.6, QO3.2 and QO5.4, one UPDATE (or INSERT ... SELECT) has a status condition, but the other statements of the same Query ID do not. If the guarded statement changes no row, the Repository rolls back all statements and throws `NoRowChangedException`. The HTTP answer is 409. The spec owner keeps this rule as a safety net: the team will probably rewrite these Query IDs as single statements (`WITH ... UPDATE ... RETURNING`, then `INSERT ... SELECT`, as QU4.3). When `queries.sql` changes, regenerate the SQL; a 0-row result then answers 409 without a rollback. | Without this, for example Q3.3 on a Confirmed appointment adds a second `AppointmentConfirmation` row. The SQL text does not change. | 2.16, 2.19 |
| D-009 | 2026-10-14 | **Q3.1.** The class list has no method for Q3.1 (the same SQL as Q2.1). It is `NotificationRepository.countUnreadOnNotificationPage`. | Rule: all 56 queries are Repository methods. | 2.18 |
| D-010 | 2026-10-14 | **Session values as parameters.** Methods whose SQL needs `:officer_id` or `:consultant_id` (for example `ClaimRepository.saveResult`, `ReportRepository.updateSignedAt`) have that value as an extra parameter. The Controller takes it from the login session. | The class diagram leaves these parameters out; the SQL needs them. | 2.18 |
| D-011 | 2026-10-14 | **QO5.2 dates.** `findFacilitySlots(facility, dates, officer_id)` takes `dateFrom` and `dateTo`, the `:date_from` and `:date_to` of the SQL. | The SQL has two dates. | 2.18 |
| D-012 | 2026-10-14 | **Old code.** The September draft code (patient screens M1 to M9, console D1 to D8, in-memory repositories, `uc_01` to `uc_11`) moved to `lib/legacy/` and `test/legacy/`, with the entry points `lib/legacy/main_patient_legacy.dart` and `lib/legacy/main_console_legacy.dart`. The old plan is `docs/legacy/IMPLEMENTATION.md`. Delete `lib/legacy/` when the officer and consultant slices are done. | The brief says the September drafts are superseded. The team agreed to replace the old code. The old console stays for comparison until O1 to C2 are built. | none |
| D-013 | 2026-10-14 | **Theme.** Seed colour #6750A4 (the Material 3 baseline primary, as in the Figma frames). A theme extension `StatusColors` gives the green success colours of the frames (#146C2E on #C4EED0), because Material 3 has no success role. | Figma page 125:2 uses the baseline palette. | 2.21 |
| D-014 | 2026-10-14 | **Login page.** Figma has no login frame. The page uses the style of U1-1 Register Page (logo, title, fields, one filled button). | The site map has Login as the root, but there is no frame for it. | 2.21, 2.22 |
| D-015 | 2026-10-14 | **Register unavailable.** `InsuredPersonModel.register` saves the claim as `Register unavailable` when `findInSSORegister` throws `RegisterUnavailableException`. The stub register is in the same database, so today only a test double throws it. | 07-open-questions.md, item 3. A real register client throws this exception when it cannot connect. | 2.13 (U1) |
| D-016 | 2026-10-14 (changed 2026-10-14 by the spec owner) | **Phone number.** The data dictionary rule: the code removes spaces, dots, dashes and brackets, changes a leading `+66` into `0`, and the result must match `^0\d{8,9}$`. Other numbers show the U1-3 error text. The normal form is saved in `InsuredPerson.phone_no`. | The spec owner chose the data dictionary rule over the U1 regular expressions (R-007). | 2.13 (U1), 2.17 |
| D-017 | 2026-10-14 | **evidence_ref of Q1.9.** `REG-<yyyyMMdd>-<claim_id, 4 digits>`, the format of the seed rows; NULL when the register is unavailable. | The U1 description does not say where `:evidence_ref` comes from. | 2.13 (U1) |
| D-018 | 2026-10-14 | **Demo register people.** `server/db/seeds/002_register_demo_people.sql` adds two ACTIVE people (1555500011122, 2555500022233) to the `master_table` stub. | All ACTIVE people of `seed.sql` are already registered, so nobody could finish U1 in the demo. | 2.17 (stub only) |
| D-019 | 2026-10-14 | **One U1 transaction.** Q1.3 to Q1.10 and the new `UserAccount` row run in one transaction; if one fails, nothing is saved and the stored files are removed.
